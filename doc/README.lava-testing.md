# CIP Core functionality testing with LAVA

This document explains how SWUpdate, Secure boot and IEC layer are being tested using LAVA. LAVA job definitions are generated by `scripts/lava_jobs.py` from YAML fragments in `tests/templates` and run on QEMU amd64, arm64 and arm and on M-COM (x86-uefi). CI jobs run until the final health of all the submitted jobs is reported.

## Job generation

* `tests/templates/blocks` and `tests/templates/steps` contain YAML fragments (header, deploy, boot and test actions, test steps). Placeholders have the form `${name}` and are replaced by `scripts/lava_jobs.py`.
* `tests/templates/jobs.yml` declares for every test (IEC, secure-boot, swupdate, kernel-panic, ...) which fragments are used, in which order, and the per-test and per-target values. See the comment at the top of the file for all keys.
* `scripts/lava_jobs.py` assembles the fragments into one job definition. `scripts/submit_lava.sh` calls it and submits the result.

Generate a job locally:

```
python3 scripts/lava_jobs.py --test swupdate --target qemu-arm64 \
    --release trixie --branch master --iec-timeout 30 --out /tmp/jobs
```

The path of the written file is printed. If a test does not exist for a target, nothing is written.

Run the unit tests:

```
python3 -m unittest discover -s tests
```

### Adding a new test

1. Add new fragments to `tests/templates/blocks` or `tests/templates/steps` if the existing ones do not fit.
2. Add an entry under `tests:` in `tests/templates/jobs.yml` listing the blocks and values.
3. Add a unit test and the test to `.gitlab-ci.yml` via `test_function`.

[tests/templates/README.md](../tests/templates/README.md) explains how a job is built and walks through examples: a new negative software update test that reuses existing blocks, a test with its own block, differences between targets (`per_arch`, M-COM), and a new placeholder.

## LAVA Setup

The above mentioned job definitions shall be sent to CIP LAVA Lab for testing. For local testing please follow the steps mentioned in [CIP LAVA Docker](https://gitlab.com/cip-project/cip-testing/lava-docker/-/tree/cip-lava-docker?ref_type=heads#linaros-automated-validation-architecture-lava-docker-container) to have your own setup.

## LAVA template variables

Available as `${name}` in the fragments:

* `branch` : The branch on which the pipeline is triggered.
* `distribution` : The `release` assigned in the gitlab CI configuration file.
* `project_url` : Default value is `https://s3.eu-central-1.amazonaws.com/download2.cip-project.org/cip-core`.
* `architecture` : The target, e.g. `qemu-arm64`.
* `context_architecture` : The architecture part of the target, used in the LAVA context.
* `imageargs` : QEMU arguments of the target; arm64 and arm additionally get the U-boot firmware binary as deploy artifact.
* `test_function` : Name of the test.
* `updatestate` : Expected bootloader environment variable (ustate) after the update.
* `job_title` : Per-test part of the job name.
* `start_monitor`, `end_monitor` : Boot messages monitored by the secure boot negative tests.
* `artifact` : Artifact manipulated by the secure boot negative tests.
* `IEC_TEST_TIMEOUT_MINUTES` : Timeout of the IEC test.
